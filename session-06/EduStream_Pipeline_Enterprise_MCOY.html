Patrones de producción

Tres patrones que marcan la diferencia

MERGE INTO idempotente

La clave de idempotencia real: re-ejecutar el pipeline N veces deja la tabla idéntica. El paso previo de deduplicación via window function garantiza que el batch entrante no tenga conflictos antes del MERGE.

pyspark dedup_window = Window.partitionBy("enrollment_id").orderBy(desc("_ingested_at")) silver_tbl.alias("t") .merge(incoming.alias("s"), "t.enrollment_id = s.enrollment_id") .whenMatchedUpdateAll() .whenNotMatchedInsertAll() .execute()

SCD Type 2 con hash SHA-256

Los cursos cambian: precio, categoría, instructor. SCD2 cierra la versión anterior e inserta la nueva — sin perder la historia. El hash determina si hubo cambio sin necesidad de comparar columna por columna.

pyspark # Hash de atributos rastreados — detecta cualquier cambio .withColumn("_scd_hash", F.sha2(F.concat_ws("||", *tracked), 256)) # Cerrar versión vieja si el hash cambió whenMatchedUpdate(set={ "is_current": F.lit(False), "valid_to": F.expr("current_date() - INTERVAL 1 DAY") })

DQ Framework con auditoría

Cada validación registra su resultado en _dq_audit con el run_id, la capa, el check y el pass_rate. Severidad block detiene el pipeline si la calidad cae bajo el 95%.

pyspark run_dq_check(df, "silver", "silver_enrollments", check="enrollment_id_unico", condition=F.col("enrollment_id").isNotNull(), severity="block") # detiene si pass_rate < 95% # Consulta de auditoría posterior # SELECT * FROM _dq_audit WHERE run_id = '...'

rescuedDataColumn + schema explícito

Doble defensa contra schema drift: el contrato explícito falla rápido ante tipos incompatibles; rescuedDataColumn captura columnas inesperadas en _rescued_data sin tumbar la carga. En DLT, expect_or_fail en esa columna detiene el pipeline.

pyspark spark.read .schema(SCHEMAS["enrollments"]) # contrato .option("rescuedDataColumn", "_rescued_data") .csv(path) # En DLT: @dlt.expect_or_fail("schema_intacto", "_rescued_data IS NULL")

Decisiones de arquitectura

Architecture Decision Records

Cada decisión de diseño documentada con su contexto, trade-offs y alternativas descartadas. Esto es lo que diferencia un pipeline de producción de un script que corre una vez.

ADR-01 MERGE INTO en silver en lugar de overwrite ▼
✓ Accepted

Decisión: silver_enrollments se actualiza con MERGE INTO, no con mode("overwrite").

Problema: El overwrite reconstruye la tabla entera en cada ejecución — no es incremental, no tolera concurrencia, y destruye el historial de Delta de forma poco controlada. Con un CSV de 5k filas no se nota; con cargas diarias acumuladas durante un año, el impacto es crítico.

Trade-off: MERGE exige una clave de negocio estable (enrollment_id) y un paso previo de deduplicación del batch. Es más código. A cambio se gana idempotencia real — re-ejecutar N veces = resultado idéntico. Propiedad verificada en test_upsert_idempotente.

Nota: Bronze sí usa overwrite — es correcto, porque bronze es un mirror del raw y reprocesarlo entero es la semántica esperada.

ADR-02 Schema explícito como data contract (no inferSchema) ▼
✓ Accepted

Problema: inferSchema lee los datos dos veces y el tipo inferido depende de los datos: un CSV donde payment_amount trae solo enteros infiere int; el siguiente con un decimal infiere double. El pipeline rompe sin que nadie cambie una línea de código.

Decisión: StructType explícito para cada entidad. El schema es un contrato: si la fuente lo viola, el pipeline falla rápido y de forma visible en vez de producir datos incorrectos en silencio. rescuedDataColumn captura columnas inesperadas sin tumbar la carga.

ADR-03 SCD Type 2 para la dimensión de cursos ▼
✓ Accepted

Problema: Los cursos cambian: sube el precio, se recategoriza, cambia el instructor. Una tabla de estado actual no puede responder "¿cuánto costaba este curso cuando el usuario X se inscribió en marzo?".

Alternativa descartada — SCD Type 1 (overwrite): más simple, pero pierde la historia irrecuperablemente. Delta time travel parece una alternativa, pero no lo es: time travel versiona la tabla entera, no la entidad de negocio, y VACUUM lo borra eventualmente.

Alternativa descartada — Delta time travel: versiona toda la tabla, no entidades individuales. No es recuperable indefinidamente (VACUUM). No es un sustituto de SCD2.

Trade-off: SCD2 multiplica filas (un curso con 5 cambios = 5 filas) y exige que gold filtre is_current = true. A cambio, la historia es permanente y recuperable por diseño.

ADR-04 DQ gating con tabla de auditoría centralizada ▼
✓ Accepted

Problema: Validar calidad con assert dispersos en el código tiene dos fallas: los resultados no quedan en ningún lado, y no hay un criterio uniforme de cuándo detener el pipeline.

Decisión: Función run_dq_check que recibe una condición booleana y una severidad (warn | block). Registra run_id, capa, check, pass_rate en _dq_audit. La calidad del pipeline pasa de ser invisible a ser una consulta SQL.

ADR-05 ZORDER hoy · Liquid Clustering como evolución ▼
→ Deferred to Liquid Clustering

Estrategia actual: OPTIMIZE ... ZORDER BY (enrolled_at) para silver_enrollments (queries temporales: cohortes, retención). ZORDER BY (course_id) para gold (queries por curso).

Alternativa descartada — particionamiento físico: Particionar por fecha produciría cientos de particiones diminutas con este volumen. El particionamiento solo conviene con tablas grandes (100+ GB) y columnas de baja cardinalidad.

Evolución: Liquid Clustering (CLUSTER BY) reemplaza a ZORDER — se adapta incrementalmente, no exige orden de columnas, permite cambiar claves sin reescribir la tabla. Es el camino natural cuando esté disponible en el tier.

Entregable bootcamp

Las 4 reflexiones del entregable

REFLEXIÓN 01

Managed vs External Table

Managed: Unity Catalog controla metadatos y archivos físicos — DROP TABLE borra ambos. External: tú defines LOCATION — DROP solo borra los metadatos, los datos persisten.

Para EduStream: managed tables. Los datos son exclusivos de la plataforma, Unity Catalog gestiona governance y lineage. External solo si un sistema externo (Redshift, otro data lake) consumiera los Parquet directamente.

REFLEXIÓN 02

Versiones acumuladas y VACUUM

Cada write retiene archivos Parquet nuevos indefinidamente. Small files problem: Spark abre un file handle por archivo — con cientos de archivos el planning overhead supera la ejecución. Storage cost escala linealmente.

VACUUM elimina archivos no referenciados fuera del retention window (7 días default). OPTIMIZE compacta — complementario, no sustituto.

REFLEXIÓN 03

expect / expect_or_drop / expect_or_fail

expect_or_drop para pagos negativos: dato corrupto sin interpretación válida → se descarta silenciosamente pero queda en las métricas de DQ.

expect para course_id nulo: puede ser estado transitorio → se conserva marcado.

expect_or_fail para schema drift (_rescued_data IS NULL): si la fuente cambió su estructura, fail-fast evita producir métricas sobre datos mal parseados.

REFLEXIÓN 04

Estrategia de ZORDER

enrolled_at para silver_enrollments: el 90% de las queries son temporales (cohortes, retención por semana). ZORDER co-localiza archivos → data skipping reduce el scan.

course_id para gold: queries filtran por curso. No particionamiento físico: con este volumen generaría cientos de particiones diminutas. Evolución natural: Liquid Clustering (CLUSTER BY).
